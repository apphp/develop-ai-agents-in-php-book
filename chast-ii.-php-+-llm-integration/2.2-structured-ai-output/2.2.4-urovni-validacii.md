# 2.2.4 Уровни валидации

Даже если используемая языковая модель поддерживает структурированные ответы, валидация данных всё равно остаётся обязательной частью системы. Нельзя полностью полагаться на то, что модель всегда вернёт корректный результат.

На практике AI может пропустить обязательное поле, вернуть значение `null`, перепутать тип данных, указать недопустимое значение из списка разрешённых вариантов, вернуть текст вместо числа или сформировать некорректный JSON. По этой причине промышленные AI-системы обычно используют несколько уровней проверки данных (validation layers).

### **Первый уровень – проверка JSON**

Сначала необходимо убедиться, что ответ модели вообще является корректным JSON-документом.

```php
$data = json_decode($response, true);

if (json_last_error() !== JSON_ERROR_NONE) {
    throw new RuntimeException('Invalid JSON');
}
```

Если JSON повреждён или содержит ошибки синтаксиса, дальнейшая обработка невозможна, поэтому выполнение должно быть остановлено на этом этапе.

### **Второй уровень – проверка структуры данных**

После успешного разбора JSON необходимо убедиться, что в ответе присутствуют все обязательные поля и что структура соответствует ожидаемому формату.

```php
if (!isset($data['sentiment'])) {
    throw new RuntimeException('Missing sentiment');
}
```

Для такой проверки часто используются специализированные инструменты, например `opis/json-schema`, `symfony/validator` или собственные валидаторы проекта.

### **Третий уровень – семантическая проверка**

Даже если JSON корректен и содержит все необходимые поля, это ещё не означает, что данные имеют смысл с точки зрения предметной области.

Например:

```json
{
  "urgency": 7.5
}
```

С точки зрения JSON такой документ полностью корректен. Однако если уровень срочности должен находиться в диапазоне от 0 до 1, то значение `7.5` является ошибочным.

Для подобных случаев используется семантическая валидация:

```php
if ($data['urgency'] < 0 || $data['urgency'] > 1) {
    throw new DomainException('Invalid urgency');
}
```

Такая проверка позволяет контролировать допустимые диапазоны значений, взаимосвязи между полями и другие ограничения предметной области.

### **Четвёртый уровень – проверка бизнес-правил**

Иногда данные являются корректными как с технической, так и с логической точки зрения, но при этом нарушают правила конкретного приложения.

Например, модель может вернуть:

```json
{
  "department": "finance"
}
```

Если система поддерживает только отделы `sales`, `support` и `billing`, то значение `finance` должно быть отклонено, несмотря на то что оно является корректной строкой.

На этом уровне проверяется соответствие данных бизнес-требованиям и внутренним правилам приложения.

### **Многоуровневая защита**

В промышленных AI-системах обычно применяется многоуровневая схема валидации. Каждый уровень проверяет данные с собственной точки зрения и перехватывает ошибки, которые не были обнаружены предыдущими проверками.

Такой подход напоминает принцип многоуровневой защиты, широко используемый в информационной безопасности. Если один механизм контроля не сработает, последующие уровни смогут обнаружить проблему и предотвратить её попадание в бизнес-логику приложения.

Архитектурно этот процесс можно представить следующим образом:

```
AI-модель
    ↓
Проверка JSON
    ↓
Проверка структуры
    ↓
Семантическая проверка
    ↓
Проверка бизнес-правил
    ↓
Бизнес-логика
```

Чем большее влияние результаты AI оказывают на работу системы, тем важнее становится наличие нескольких независимых уровней валидации. Это позволяет существенно повысить надёжность и предсказуемость поведения приложения.
