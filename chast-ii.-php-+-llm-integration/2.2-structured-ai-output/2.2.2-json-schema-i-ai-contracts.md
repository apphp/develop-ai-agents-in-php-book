# 2.2.2 JSON Schema и AI contracts

### JSON-схема и контракты взаимодействия с AI

Структурированный вывод означает, что модель должна вернуть результат в заранее определённом формате. Чаще всего для этого используется JSON.

Например, система поддержки клиентов может ожидать от модели такой ответ:

```json
{
  "sentiment": "negative",
  "urgency": 0.82,
  "summary": "Клиент жалуется на отсутствие ответа",
  "department": "support"
}
```

В этом случае искусственный интеллект становится частью инженерной системы, а не просто инструментом для генерации текста. Его работа начинает напоминать обычное взаимодействие через программный интерфейс с чётко определёнными правилами обмена данными.

### Использование JSON-схемы

В рабочих системах для описания структуры ответа чаще всего применяется JSON-схема. Она позволяет заранее определить, какие поля должны присутствовать в ответе, какие типы данных они содержат и какие ограничения к ним применяются.

Пример схемы:

```json
{
  "type": "object",
  "properties": {
    "sentiment": {
      "type": "string",
      "enum": ["positive", "neutral", "negative"]
    },
    "urgency": {
      "type": "number",
      "minimum": 0,
      "maximum": 1
    },
    "summary": {
      "type": "string"
    }
  },
  "required": [
    "sentiment",
    "urgency",
    "summary"
  ]
}
```

Теперь приложение может проверять корректность ответа модели так же, как проверяет ответы любого REST API.

### Почему схема важнее инструкций в запросе

Многие начинающие разработчики пытаются добиться нужного формата ответа только с помощью инструкций в запросе:

> Ответь строго в формате JSON.\
> Не добавляй никакого дополнительного текста.

Такой подход может работать во время экспериментов, но он не гарантирует стабильный результат.

Нельзя строить рабочую систему на предположении, что модель всегда будет точно следовать инструкциям. Вместо этого система должна самостоятельно контролировать качество ответа.

Для надёжной работы обычно используются:

* схема данных
* проверка корректности ответа
* повторные попытки выполнения запроса
* механизмы восстановления после ошибок
* мониторинг работы системы
* логика резервного переключения на другие модели или сервисы

### Ответ модели как контракт

В рабочей среде языковая модель рассматривается как сервис, который обязан соблюдать определённый контракт взаимодействия.

Последовательность обработки данных обычно выглядит так:

```
Входные данные → Схема → Проверка → Бизнес-логика
```

Такой подход позволяет сделать поведение модели более предсказуемым и уменьшить влияние случайности на работу приложения.

### Математическая идея структурированного вывода

Структурированный вывод можно рассматривать как ограничение множества возможных ответов, которые модель может сгенерировать.

Без схемы модель выбирает ответ из огромного пространства возможных текстов:

$$
|\Omega_{plain}| \gg |\Omega_{schema}|
$$

где:

* $$\Omega_{plain}$$ — множество всех возможных текстовых ответов;
* $$\Omega_{schema}$$ — множество ответов, соответствующих заданной структуре.

Чем меньше количество допустимых вариантов ответа, тем ниже неопределённость результата и тем стабильнее работает система.

Именно поэтому современные решения на базе искусственного интеллекта всё чаще строятся вокруг структурированных данных, а не вокруг свободного текстового вывода.
