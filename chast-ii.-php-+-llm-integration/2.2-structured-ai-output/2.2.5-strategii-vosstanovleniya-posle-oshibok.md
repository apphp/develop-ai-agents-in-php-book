# 2.2.5 Стратегии восстановления после ошибок

Даже современные языковые модели периодически генерируют некорректные ответы. Они могут возвращать данные в неправильном формате, нарушать структуру JSON или выдавать значения, не соответствующие требованиям системы. Поэтому промышленная AI-система должна не только обнаруживать ошибки, но и уметь восстанавливаться после них. Таким образом нам нужны recovery strategies.

### **Повторная отправка запроса**

Самая простая стратегия восстановления заключается в повторном обращении к модели (retry strategy). Если ответ не проходит проверку, система автоматически выполняет новый запрос.

```php
for ($i = 0; $i < 3; $i++) {

    $response = $llm->generate($prompt);

    if ($validator->isValid($response)) {
        return $response;
    }
}
```

На практике многие ошибки возникают случайно, поэтому повторный запрос нередко позволяет получить корректный результат без дополнительных действий.

### **Самокоррекция ответа**

В некоторых случаях системе проще показать модели её собственную ошибку и попросить исправить результат (self-healing prompt).

Например:

```
Ваш JSON некорректен.
Поле urgency должно быть числом от 0 до 1.
Исправьте ответ.
```

Такой подход часто показывает хорошие результаты, поскольку модель получает конкретную информацию о причине ошибки и может скорректировать ответ без повторного выполнения всей задачи.

### **Резервная модель**

Если основная модель не смогла сформировать корректный результат после нескольких попыток, система может передать задачу другой модели (fallback model).

Пример цепочки обработки:

```
GPT-5 → Claude → Локальная модель
```

Подобный механизм особенно важен в распределённых AI-платформах, где надёжность системы зависит не от одной модели, а от возможности переключаться между несколькими поставщиками.

### **Частичное восстановление данных**

Иногда ответ содержит большую часть необходимой информации, а ошибка затрагивает только отдельные поля.

Например:

```json
{
  "sentiment": "negative",
  "summary": "..."
}
```

Если поле `urgency` отсутствует, система не обязательно должна заново генерировать весь ответ. Вместо этого можно использовать несколько вариантов восстановления:

* вычислить значение по дополнительным правилам
* повторно запросить только отсутствующее поле
* подставить значение по умолчанию

Такой подход (partial recovery) уменьшает задержки и снижает количество обращений к модели.

### **Передача задачи человеку**

Не все ошибки можно исправить автоматически. Иногда модель демонстрирует низкую уверенность в результате, данные противоречат друг другу или решение требует экспертной оценки.

В таких ситуациях система передаёт задачу человеку для проверки (human escalation):

```
Низкая уверенность модели → Проверка человеком
```

Этот механизм часто используется в финансовых, юридических, медицинских и других системах, где цена ошибки слишком высока для полностью автоматической обработки.

### **Отказоустойчивая архитектура**

На практике промышленные AI-системы редко ограничиваются одной стратегией восстановления. Обычно используется комбинация нескольких механизмов: повторные запросы, самокоррекция, резервные модели, частичное восстановление данных и передача сложных случаев человеку.

Архитектурно процесс может выглядеть следующим образом:

```
AI-модель
    ↓
Валидация
    ↓
Ошибка?
    ↓
Повторный запрос
    ↓
Самокоррекция
    ↓
Резервная модель
    ↓
Проверка человеком
```

Такой многоуровневый подход позволяет значительно повысить надёжность AI-системы и обеспечить стабильную работу даже в ситуациях, когда модель возвращает некорректные результаты.
