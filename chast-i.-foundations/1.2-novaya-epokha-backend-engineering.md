# 1.2 Новая эпоха backend engineering

#### От CRUD-сервисов к AI-native платформам

Еще совсем недавно backend-разработка выглядела относительно предсказуемо. Почти любая система строилась вокруг понятного и довольно линейного набора компонентов: API, база данных, очереди, кэш, бизнес-логика. Backend-инженер проектировал маршруты запросов, продумывал структуру таблиц, оптимизировал SQL и следил за тем, чтобы все работало стабильно и детерминированно.

Типичный backend-процесс выглядел примерно одинаково:

```
Request → Validation → Business Logic → Database → Response
```

Если на вход приходили одинаковые данные, система должна была вернуть одинаковый результат. В этом и заключалась одна из фундаментальных идей классического backend engineering – предсказуемость.

Появление больших языковых моделей изменило эту картину намного сильнее, чем многие ожидали. Сначала LLM воспринимались как очередной внешний API. Казалось, что это просто более умный chatbot, который можно встроить в существующее приложение. Но довольно быстро стало понятно, что речь идет о гораздо более глубоком изменении.

LLM добавили в software stack новый тип вычислений – вероятностный и семантический.

Впервые backend начал работать не только с четко структурированными данными, но и с человеческим языком, контекстом, намерениями и неоднозначностью. Раньше backend-система отвечала на вопрос: "Что нужно сделать?" Теперь ей все чаще приходится отвечать на другой вопрос: "Что пользователь имел в виду?"

Это звучит как небольшое изменение формулировки, но на практике именно здесь начинается новая эпоха backend engineering.

### Backend впервые стал недетерминированным

Классические backend-системы всегда стремились минимизировать неопределенность. Инженеры боролись за повторяемость, последовательность и предсказуемость поведения. В AI-системах ситуация почти противоположная. Языковая модель по своей природе работает вероятностно.

В упрощенном виде LLM пытается предсказать наиболее вероятный следующий токен на основе предыдущего контекста:

$$
P(w_t \mid w_1,w_2,...,w_{t-1})
$$

Это означает, что AI backend начинает жить в мире вероятностей. Инженеру уже недостаточно просто проверить правильность бизнес-логики. Теперь возникают мысли об уверенности, галлюцинациях, нестабильности, общественном контексте и стоимости инференса.&#x20;

Фактически современный AI backend оказался где-то между распределенными системами и машинным обучением.

### Почему AI становится новым runtime layer

История разработки программного обеспечения во многом представляет собой историю появления новых уровней абстракции.

Сначала разработчики работали практически напрямую с железом. Затем появились операционные системы. После этого – виртуальные машины, облачные платформы, контейнеры и системы оркестрации.

Сегодня формируется еще один слой – AI runtime layer.

Традиционный runtime отвечает за исполнение кода. JVM исполняет Java, Node.js исполняет JavaScript, PHP Runtime исполняет PHP-код.

Но LLM начинают выполнять другую функцию. Они интерпретируют человеческое намерение и превращают его в действия.

Схематично это выглядит так:

```
Application
    ↓
AI Runtime
    ↓
Operating System
    ↓
Hardware
```

AI runtime способен анализировать запрос пользователя, выбирать инструменты, генерировать план действий, обращаться к памяти системы и даже принимать промежуточные решения по ходу выполнения задачи.

По сути, модель постепенно превращается в когнитивный процессор приложения.

### AI-agent системы и классические backend-системы

Классическая backend-система обычно представляет собой набор заранее определенных сервисов. Архитектура таких систем довольно жесткая: API Gateway вызывает нужный сервис, сервис обращается к базе данных, затем возвращает результат.

Все маршруты известны заранее.

AI-agent системы работают иначе. Агенту можно дать высокоуровневую задачу, а детали выполнения он определит сам.

Представим запрос:

> "Найди лучшие ноутбуки для ML до $2500 и сравни их."

Для классического backend это почти неразрешимая задача. Что означает "лучшие"? Какие характеристики важны для ML? Как сравнивать устройства?

AI-agent пайплайн способен самостоятельно разбить задачу на этапы. Сначала определить намерение пользователя, затем выполнить поиск, извлечь характеристики устройств, провести рассуждение и только после этого сгенерировать итоговую рекомендацию.

```
Intent Detection
    ↓
Web Search
    ↓
Data Extraction
    ↓
Reasoning
    ↓
Generated Recommendation
```

Такой backend уже нельзя назвать обычной CRUD-системой. Это уже [reasoning system](../vvedenie/glossarii.md#reasoning-system).

### AI – это не просто chatbot

Одна из самых частых ошибок при обсуждении AI заключается в том, что люди воспринимают его исключительно как chat interface.

На самом деле chat – лишь внешний слой.

Главная революция происходит внутри уровня оркестровки. Современная AI-система обычно включает retrieval pipelines, vector databases, memory systems, tool execution, observability, evaluation и сложную логику маршрутизации запросов.

Когда пользователь отправляет сообщение в AI-приложение, под капотом может происходить целая цепочка операций: генерация эмбеддингов, поиск по векторной базе данных, выбор подходящего агента, вызов внешних API, сбор контекста, построение цепочки рассуждений и только потом – обращение к LLM.

То есть AI-система – это уже полноценная распределенная платформа (distributed platform).

### AI как инфраструктурная проблема

На раннем этапе многим казалось, что интеграция AI сводится к подключению OpenAI API.

На практике production AI-системы очень быстро превращаются в инфраструктурную задачу.

Появляются проблемы latency, retries, token cost, provider failover, context management, prompt versioning и observability. Возникает необходимость хранить embeddings, индексировать данные для semantic search и строить evaluation pipelines.

Типичная архитектура production AI-platform сегодня выглядит примерно так:

```
Client
  ↓
API Gateway
  ↓
AI Orchestrator
  ↓
Prompt Pipeline
  ↓
LLM Provider Layer
  ↓
Tools / Memory / RAG
```

Именно orchestration layer становится сердцем системы.

### Экономика AI-систем

У классического backend стоимость инфраструктуры в основном определяется CPU, памятью, storage и network traffic.

В AI-системах появляется новая единица стоимости – токены.

genui{"math\_block\_widget\_always\_prefetch\_v2":{"content":"Cost = Tokens\_{input} + Tokens\_{output}"\}}

Это меняет мышление инженеров. Теперь даже неудачный prompt способен напрямую влиять на расходы компании. Слишком длинный context window может резко увеличить стоимость inference, а плохо спроектированный агент – бесконтрольно расходовать бюджет.

AI неожиданно становится частью FinOps.

### PHP и AI: мифы и реальность

Когда люди слышат про AI, они почти автоматически думают о Python. И действительно, Python абсолютно доминирует в training, deep learning research и data science.

Но production AI systems – это не только обучение моделей.

Огромная часть реальных AI-продуктов состоит из API, orchestration, integrations, очередей, workflow management, бизнес-логики и инфраструктурных сервисов.

А это именно та область, где PHP исторически чувствует себя очень уверенно.

PHP отлично подходит для построения AI orchestration layer. Современные AI backend-системы в значительной степени состоят из сетевых запросов, обработки событий, интеграций и управления workflow.

### AI-системы становятся event-driven

Еще одна важная особенность современных AI-platform – они все чаще строятся как event-driven systems.

Обычный synchronous request-response workflow плохо подходит для сложных AI-пайплайнов. Многие операции занимают заметное время: OCR, embedding generation, indexing, summarization, classification.

Поэтому AI workflow часто разбивается на цепочку событий:

```
User Uploads Document
        ↓
OCR Event
        ↓
Embedding Generation
        ↓
Vector Indexing
        ↓
Summarization
        ↓
Classification
```

Каждый этап может выполняться независимо, масштабироваться отдельно и запускаться через очереди.

### Архитектура современных AI-систем

Современная AI-платформа обычно состоит из нескольких уровней.

В нижней части находятся LLM providers – например, entity\["company","OpenAI","AI company"], entity\["company","Anthropic","AI company"] или entity\["company","Google","Technology company"]. Над ними располагается orchestration layer, который управляет prompt'ами, routing, retries и memory.

Далее появляется retrieval layer с embeddings и vector search. Отдельно существует memory layer, отвечающий за conversation history, long-term memory и состояние агентов.

Поверх этого располагается tool layer – интеграции с внешними сервисами, базами данных, CRM, email и другими системами.

И наконец, возникает evaluation layer. Обычные unit-тесты уже не способны полноценно проверить AI-систему. Поэтому появляются prompt evaluation, hallucination scoring и benchmark datasets.

### Почему observability становится критически важной

В классическом backend debugging обычно сводился к анализу логов и stack trace.

В AI-системах этого уже недостаточно.

Теперь нужно отслеживать prompts, model versions, token usage, reasoning chains, tool calls и состояние контекста. Иногда две одинаковые user-команды могут приводить к разным intermediate reasoning paths.

Из-за этого AI observability постепенно превращается в отдельную инженерную дисциплину.

### Сквозной проект книги

На протяжении книги мы будем строить полноценную AI Operations Platform.

Это будет не toy-проект и не простой chatbot поверх OpenAI API. Мы будем постепенно проектировать production-oriented AI system с агентами, orchestration engine, memory layer, vector search, observability и event-driven архитектурой.

Финальная система будет включать AI agents, long-running workflows, queues, RAG, multi-provider поддержку моделей и tool execution.

Архитурно проект будет выглядеть примерно так:

```
Frontend
    ↓
PHP API Platform
    ↓
AI Orchestrator
    ↓
Agent Runtime
    ↓
Tools / Memory / RAG
    ↓
LLM Providers
```

К концу книги у вас должно сформироваться не только понимание отдельных AI-технологий, но и целостное инженерное мышление вокруг AI systems.

Потому что современный backend-инженер постепенно превращается не просто в разработчика бизнес-логики, а в AI systems engineer – человека, который проектирует reasoning pipelines, orchestration architecture и инфраструктуру для интеллектуальных систем.

И в этой новой эпохе PHP находится намного в более сильной позиции, чем принято думать.

Потому что AI-революция – это не только модели.

Это инфраструктура, orchestration, distributed systems, integrations и production engineering.

А backend-разработка всегда была именно про это.
