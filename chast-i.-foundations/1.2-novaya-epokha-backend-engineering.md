# 1.2 Новая эпоха backend engineering

### 1.2 Новая эпоха backend engineering

Еще несколько лет назад backend-разработка выглядела относительно предсказуемо.\
Есть API. Есть база данных. Есть очереди. Есть бизнес-логика.\
Backend-инженер строил систему вокруг четко определенных правил:

```
Request → Validation → Business Logic → Database → Response
```

Системы были детерминированными.\
Если на вход приходили одинаковые данные – на выходе ожидался одинаковый результат.

Появление больших языковых моделей (LLM) radically изменило саму природу backend engineering. Мы впервые получили компонент инфраструктуры, который:

– умеет интерпретировать человеческий язык\
– способен рассуждать\
– генерирует новый контент\
– может принимать вероятностные решения\
– взаимодействует с внешними инструментами\
– обладает “памятью” и контекстом\
– работает как универсальный cognitive layer поверх software stack

Это уже не просто новая библиотека.\
И не просто очередной API.

Это смена архитектурной парадигмы.

***

### Что изменилось после появления LLM

До LLM backend-системы в основном работали с:

– structured data\
– deterministic logic\
– explicit workflows

После появления LLM backend начал работать с:

– неструктурированным текстом\
– контекстом\
– намерением пользователя\
– вероятностными ответами\
– reasoning pipeline\
– semantic search\
– embeddings\
– агентными workflow

Классический backend отвечал на вопрос:

“Что делать?”

AI backend начал отвечать на вопрос:

“Что пользователь имел в виду?”

Это огромная разница.

***

#### Классическая backend-модель

```
User → REST API → Service → SQL → JSON
```

Все заранее определено.

***

#### AI-native backend-модель

```
User
  ↓
LLM Orchestrator
  ↓
Tools / Agents / Memory / Vector DB
  ↓
Reasoning Loop
  ↓
Generated Action
```

Теперь система может:

– сама выбирать инструменты\
– строить план действий\
– интерпретировать неоднозначные запросы\
– выполнять цепочки reasoning\
– динамически генерировать workflow

***

### Backend впервые стал “недетерминированным”

Это одно из самых важных изменений.

Раньше backend-инженеры старались максимально убрать вероятность и неопределенность.

AI-системы, наоборот, построены на вероятностях.

LLM по сути предсказывает следующее слово.

Математически это выглядит так:

P(w\_t \mid w\_1, w\_2, ..., w\_{t-1})

Где модель вычисляет вероятность следующего токена на основе предыдущего контекста.

Для наглядности:

P(w\_t \mid w\_1,w\_2,...,w\_{t-1})

Backend-разработчику теперь приходится думать не только о correctness, но и о:

– confidence\
– hallucinations\
– context windows\
– token economics\
– prompt reliability\
– semantic consistency

Это уже ближе к distributed systems + machine learning одновременно.

***

### Почему AI – это новый runtime layer

Исторически software stack развивался слоями.

Сначала появился hardware layer.\
Потом operating systems.\
Потом virtual machines.\
Потом cloud platforms.\
Потом containers и orchestration.

Теперь появился AI runtime layer.

***

#### Что такое runtime layer

Runtime layer – это среда, в которой исполняется логика приложения.

Например:

– JVM для Java\
– PHP Runtime для PHP\
– Node.js runtime для JavaScript

Но LLM начинает играть новую роль:

```
Application
    ↓
AI Runtime
    ↓
Operating System
    ↓
Hardware
```

AI runtime:

– интерпретирует намерения\
– принимает решения\
– выбирает инструменты\
– преобразует natural language в executable actions

По сути, модель становится “когнитивным процессором” системы.

***

### Почему AI-agent systems отличаются от классических backend systems

Классическая backend-система обычно строится как набор сервисов.

Например:

```
API Gateway
    ↓
Auth Service
    ↓
Payment Service
    ↓
Notification Service
```

Все связи заранее известны.

***

AI-agent systems работают иначе.

Агент может:

– анализировать задачу\
– строить план\
– выбирать инструменты\
– выполнять несколько шагов\
– менять стратегию по ходу выполнения

***

#### Пример

Пользователь пишет:

“Найди мне лучшие ноутбуки для ML до $2500 и сравни их.”

Классический backend не знает, что такое “лучшие”.\
Не знает, что такое ML-задачи.\
Не умеет сравнивать.

AI-agent pipeline:

```
Intent Detection
    ↓
Web Search
    ↓
Product Extraction
    ↓
Reasoning
    ↓
Comparison
    ↓
Generated Recommendation
```

Это уже не CRUD-система.

Это reasoning system.

***

Это одно из самых опасных заблуждений.

LLM часто воспринимают как fancy UI поверх chat interface.

Но настоящая революция происходит не в chat UI, а в orchestration layer.

Современные AI-системы включают:

– retrieval systems\
– vector databases\
– memory layers\
– planning engines\
– tool execution\
– agent routing\
– event pipelines\
– observability\
– evaluation systems

Chat – это только интерфейс.

Под капотом работают полноценные distributed AI systems.

### AI как инфраструктурная проблема

На раннем этапе многие думали:

“Просто подключим OpenAI API.”

Но production AI-системы быстро превращаются в инфраструктурную задачу.

***

#### Типичная AI production architecture

```
Client
  ↓
API Gateway
  ↓
AI Orchestrator
  ↓
Prompt Pipeline
  ↓
LLM Provider Layer
  ↓
Tools / RAG / Memory
  ↓
Observability + Evaluation
```

Появляются новые инфраструктурные проблемы:

– latency\
– token cost\
– retries\
– provider failover\
– hallucination detection\
– context compression\
– vector indexing\
– prompt versioning\
– evaluation pipelines\
– safety systems

***

### Математика стоимости AI

У классического backend стоимость обычно зависит от:

– CPU\
– RAM\
– storage\
– network

У AI-систем появляется новая единица стоимости:

\text{Cost} = \text{Tokens}\_{input} + \text{Tokens}\_{output}

Cost = Tokens\_{input} + Tokens\_{output}

А значит:

– плохой prompt может стоить дорого\
– длинный context window увеличивает расходы\
– бесконтрольные агенты могут сжигать бюджет

AI suddenly становится частью FinOps.


```
        ↓
Embedding Generation
        ↓
Vector Indexing
        ↓

        ↓

        ↓
```

Каждый шаг может:

– занимать время\
