# 1.2.4 AI как инфраструктурная проблема

Сначала многим казалось, что внедрить AI очень просто – достаточно подключить API OpenAI, и система готова.

Но когда AI начинают использовать в реальном продукте, быстро выясняется, что это уже не просто работа с API, а полноценная инфраструктурная задача.

Почти сразу появляются новые проблемы. Нужно следить за скоростью ответов модели, обрабатывать ошибки и повторные запросы, контролировать расходы на токены и уметь переключаться между разными AI-провайдерами, если один из них недоступен.

Кроме этого, возникает необходимость управлять контекстом диалогов, хранить и обновлять промпты, а также отслеживать работу всей системы через мониторинг и аналитику.

Со временем инфраструктура становится ещё сложнее. Система должна хранить эмбеддинги, индексировать данные для семантического поиска и запускать пайплайны для проверки качества моделей.

Поэтому современная AI-платформа обычно строится как многоуровневая архитектура:

```
Client
  ↓
API Gateway
  ↓
AI Orchestrator
  ↓
Prompt Pipeline
  ↓
LLM Provider Layer
  ↓
Tools / Memory / RAG
```

Центральной частью всей этой архитектуры постепенно становится уровень оркестровки.

Именно он координирует работу моделей, промптов, памяти, инструментов и внешних сервисов. По сути, оркестратор становится главным управляющим механизмом всей AI-платформы.
