# 1.3.10 Почему AI-системы должны быть детерминированными поверх вероятностных моделей

Современные LLM работают как вероятностные системы. Они не вычисляют единственно правильный ответ, а предсказывают наиболее вероятное продолжение текста. Именно поэтому AI-системы нельзя строить так, чтобы модель напрямую выполняла критические действия.

Главный принцип современной разработки AI-систем заключается в том, что LLM не должна быть слоем выполнения. Её задача – анализировать запрос, рассуждать и генерировать гипотезы. Выполнение действий должно происходить только через детерминированный и контролируемый слой системы.

### Как выглядит правильная архитектура

В надёжных AI-системах запрос проходит несколько этапов обработки:

```
User Request
 ↓
LLM reasoning
 ↓
Structured output
 ↓
Validation
 ↓
Policy checks
 ↓
Deterministic execution
 ↓
Result
```

Сначала модель анализирует задачу и формирует структурированный ответ. Затем этот ответ проверяется валидаторами, policy-правилами и системами безопасности. И только после этого происходит выполнение действия.

Такой подход позволяет сделать поведение системы предсказуемым и безопасным.

### Пример: плохой и хороший подход

Плохой подход – позволять модели напрямую выполнять команды:

```
"LLM, выполни SQL..."
```

Это опасно, потому что модель может ошибиться, сгенерировать некорректный запрос или выполнить нежелательное действие.

Правильный подход выглядит иначе:

```
LLM → SQL draft
↓
SQL parser
↓
validation
↓
permissions
↓
execution
```

В этом случае LLM только предлагает SQL-запрос, а вся дальнейшая обработка выполняется детерминированными компонентами системы.

### Почему это особенно важно для AI-agents

AI-агенты без ограничений могут быть крайне опасны. Если агенту дать возможность самостоятельно выполнять действия без контроля, он может:

* удалить данные
* вызвать дорогой API
* зациклиться
* выполнить небезопасные действия

Поэтому современные агентные архитектуры строятся вокруг механизмов контроля и ограничений.

Обычно для этого используются:

* валидаторы
* типизированные выходные данные
* схемы
* ограничения
* механизмы политик
* ограничения рабочих процессов

Эти компоненты позволяют ограничить поведение модели и превратить вероятностное рассуждение в безопасную и управляемую систему.

### Пример структурированного вывода на PHP

Даже базовая проверка структурированного вывода уже значительно повышает надёжность системы.

Ниже пример, где приложение проверяет структуру ответа модели и разрешённые действия перед выполнением:

```php
$response = json_decode($llmOutput, true);

if (!isset($response['action'])) {
    throw new Exception('Invalid schema');
}

$allowedActions = ['search', 'summarize'];

if (!in_array($response['action'], $allowedActions)) {
    throw new Exception('Forbidden action');
}

executeAction($response);
```

В этом примере модель не может выполнить произвольное действие. Система сначала проверяет схему ответа и убеждается, что действие входит в список разрешённых операций. Только после этого вызывается уровень выполнения.
